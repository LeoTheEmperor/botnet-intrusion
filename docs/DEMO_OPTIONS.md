# Demo options: a ladder of fallbacks

Always know your next rung. Every rung below was run end to end during development; the Raspberry Pi rung is the only one that has not yet run on a Pi.

| # | Demo | Command | What is real | What is not | Needs |
|---|---|---|---|---|---|
| 1 | **Pi live** | `sudo python3 src/live_detector.py detect --iface wlan0 --model models/live_model.npz --dashboard 8080 --dashboard-host 0.0.0.0`, attacks from the laptop with `traffic_sim.py` | real packets, real hardware and network, a model trained on that network's traffic | the attacks are generated by us, not real botnets | Pi, own network, laptop |
| 2 | **Dataset replay** (best fallback; also runs on the Pi) | `python src/demo_nbaiot.py` (add `--mode time` for the honest setting) | real N-BaIoT feature rows from an infected device, the real trained model, 11 classes with ground truth shown | not live packets: held-out rows are replayed | numpy only |
| 3 | **Laptop live** | `sudo python3 src/demo_loopback.py` | live packet capture, feature extraction, classification and dashboard running together | traffic generated by us over the loopback interface | Linux or WSL2, root, numpy |
| 4 | **Synthetic replay** | `python src/demo_replay.py` | the detector and dashboard, fed recorded packets | the traffic is synthetic | numpy + scapy, any OS |
| 5 | **Recording** | a screen recording of the dashboard during a successful run, plus a phone video of the LEDs, plus screenshots in the slides | what actually happened on your best run | it is a recording | made before the evaluation |

Rungs 2 and 4 work on Windows. Rung 3 needs Linux or WSL2 (raw sockets). Rung 2 needs no network at all.

## What to say (keep it honest)

- **Rung 1:** "A Raspberry Pi captures its own Wi-Fi traffic; a second machine on our isolated network generates SYN floods, UDP floods and port scans. The model was trained on traffic recorded on this network."
- **Rung 2:** "These are real feature rows from an infected doorbell in the N-BaIoT dataset, replayed through our from-scratch forest. The thin strip is the ground truth. In the honest mode the model was trained on early traffic and replayed on late traffic, so you can see junk being mistaken for combo, which is the drift and overlap finding in the report."
- **Rung 3:** "The whole pipeline running live on one computer: real packets from the kernel, traffic generated locally."
- **Rung 4:** "Synthetic traffic replayed through the same detector and dashboard; it shows the pipeline works, not real-world accuracy."
- Never present a replay as live attack detection on real botnets.

## 30-second triage on the day

| Problem | Do this |
|---|---|
| Pi does not boot or the network is down | run rung 2 on the laptop (`python src/demo_nbaiot.py`) |
| Pi boots but live capture or Wi-Fi fails | run rung 2 on the Pi itself (`python3 src/demo_nbaiot.py --lan`, open the page from the laptop) or on the laptop |
| Attacks do not trigger alerts | lower or raise `--rate`, check the interface name and that `sudo` is used; otherwise switch to rung 2 |
| Dashboard unreachable from the laptop | open it on the Pi's own network or use rung 2 on the laptop |
| Laptop problem | use the Pi's dashboard on a phone, or rung 5 |

## Before the evaluation

1. Run rungs 2, 3 and 4 once each so you have seen them work; keep `demo_nbaiot.py` ready in a second terminal.
2. Record rung 5 right after your best live run (screen recording of the dashboard, video of the LEDs) and put screenshots in the slides.
3. Know the numbers: 99.90% (random split), 96.14% (interleaved blocks), 82.27% (time-ordered); the replay demos echo them.
4. Rebuild the dataset bundle only if you change the model: `python src/build_demo_bundle.py` (needs the dataset in `data/raw`).
